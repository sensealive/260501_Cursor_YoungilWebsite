# [260501_Cursor_YoungilWebsite] Project Lessons 기록

## 2026-05-27 작업 회고

### 오늘의 목표

영일엔지니어링 회사 웹사이트를 정적 HTML/CSS/JavaScript 기반으로 제작하고, 로컬 Node 서버와 GitHub Pages 배포 환경에서 모두 확인 가능한 형태로 유지보수한다.

처음에는 회사 소개, 사업 소개, 고객센터, 채용 페이지를 정적 페이지로 구성하는 단순한 작업처럼 보였다. 그러나 실제 제작 과정에서는 원본 백업 폴더 보호, GitHub Pages의 정적 호스팅 제약, 게시판 저장 방식, 로고와 이미지 경로, 캐시, 요일별 테마, 문의 폼의 실제 동작 여부, 배포 바로가기 관리가 맞물리며 여러 차례 보완이 필요했다.

이 문서는 같은 시행착오를 반복하지 않기 위한 재발 방지 기록이다.

## 실패와 원인

### 1. GitHub Pages에서 로컬 서버 API를 그대로 기대함

초기 게시판 구현은 `server.js`의 `/api/notices`, `/api/media` API가 동작한다는 전제에 가까웠다. 하지만 GitHub Pages는 정적 호스팅이므로 Node 서버 API와 파일 쓰기 기능이 실행되지 않는다. 그 결과 배포 환경에서는 게시글 목록, 작성, 수정, 삭제 방식이 로컬과 다르게 처리되어야 했다.

재발 방지:

- GitHub Pages 배포 대상 기능은 정적 파일만으로 동작 가능한지 먼저 확인한다.
- `localhost:3000`과 `github.io`를 같은 실행 환경으로 보지 않는다.
- 서버 저장이 필요한 기능은 별도 백엔드, 외부 API, 또는 정적 모드 제한 사항을 문서화한 뒤 구현한다.

### 2. 게시판 편집을 GitHub API로 직접 처리하려다 운영 부담이 커짐

한때 GitHub Pages 모드에서 GitHub Contents API와 개인 토큰을 이용해 `data/*.json`을 수정하는 방향이 들어갔다. 이 방식은 기술적으로 가능하지만, 브라우저에 토큰을 입력해야 하고 권한/보안/사용성 부담이 크다. 이후 정적 모드에서는 브라우저 `localStorage`에만 저장하는 방식으로 단순화되었다.

재발 방지:

- 공개 정적 사이트에서 관리자 토큰을 브라우저에 노출하는 구조는 피한다.
- 정적 모드의 편집은 “해당 브라우저에만 저장됨”이라는 한계를 명확히 이해한다.
- 실제 운영 게시판이 필요하면 GitHub API 우회보다 서버 API 또는 관리형 CMS를 검토한다.

### 3. 로컬 정적 접속과 Node 서버 접속을 구분하지 못함

처음에는 정적 모드를 `github.io` 여부로만 판단했다. 이 경우 `file://`로 직접 열거나 다른 정적 미리보기 환경에서 접속하면 로컬 서버 모드처럼 동작하지 않아 로그인과 게시판 저장 방식이 꼬일 수 있었다. 이후 `localhost:3000`에서만 Node 서버 모드로 보고, 그 외 환경은 정적 모드로 보는 방식으로 정리했다.

재발 방지:

- 실행 모드는 도메인 이름 하나가 아니라 실제 서버 API 사용 가능성으로 판단한다.
- `localhost:3000`은 Node 서버 모드, `file://`와 GitHub Pages는 정적 모드로 구분한다.
- 게시판 변경 후에는 `node server.js`, `file://`, GitHub Pages 세 환경을 따로 확인한다.

### 4. 로고 이미지 경로와 캐시 문제로 GitHub Pages에서 로딩 실패

로고를 `assets/logo.png`로 참조했지만, 배포 환경에서 로고가 갱신되지 않거나 로딩되지 않는 문제가 발생했다. 이후 `common.js`에 캐시 버전 쿼리(`?v=20260515`)를 붙이고 로고 데이터를 직접 포함하는 방식으로 보완했다. 근본 원인은 배포 후 실제 URL 기준의 에셋 경로와 캐시 검증을 충분히 하지 않은 것이다.

재발 방지:

- 이미지와 스크립트 변경 후 GitHub Pages 실제 URL에서 강력 새로고침으로 확인한다.
- 공용 JS/CSS를 바꾸면 필요한 경우 버전 쿼리를 함께 갱신한다.
- 에셋 경로는 로컬 파일 경로가 아니라 배포 URL 기준으로 확인한다.

### 5. `.url` 바로가기 파일에 한글/비ASCII 경로를 그대로 넣을 위험

프로젝트 운영 규칙에는 배포 후 `ShortCut` 폴더에 URL 바로가기를 생성하도록 되어 있다. 이때 `.url` 파일은 ASCII, 즉 퍼센트 인코딩된 URL만 저장해야 한다. 한글이나 특수문자가 그대로 들어가면 Windows 바로가기에서 열리지 않거나 다른 환경에서 깨질 수 있다.

재발 방지:

- `.url` 파일에는 항상 ASCII URL만 저장한다.
- 바로가기 생성 후 실제 브라우저에서 접속되는지 확인한다.
- GitHub Pages URL은 `https://sensealive.github.io/260501_Cursor_YoungilWebsite/index.html` 형식을 기준으로 검증한다.

### 6. 원본 백업 폴더 보호 규칙을 뒤늦게 명문화함

프로젝트 규칙에 `OfficialWebsite`와 `OfficialWebsite(Org Backup)` 폴더는 원본 백업용이므로 절대 수정하거나 push/pull하지 말라고 명시되어 있다. 이 규칙이 없거나 흐릿하면 원본 백업을 작업 대상으로 착각해 덮어쓸 수 있다.

재발 방지:

- 작업 전 `.cursor/rules/project-rules.mdc`를 먼저 확인한다.
- `OfficialWebsite`, `OfficialWebsite(Org Backup)`는 읽기 참고만 하고 수정하지 않는다.
- git 작업 전 `.gitignore`와 `git status`로 백업 폴더가 추적되지 않는지 확인한다.

### 7. 문의 폼이 실제 메일 발송처럼 보일 수 있음

`contact.html`의 문의 폼은 현재 화면상 등록 성공 메시지를 보여줄 수 있지만 실제 메일 발송 기능은 없다. TODO에도 서버 API나 EmailJS/Formspree 같은 폼 전송 서비스가 필요하다고 기록되어 있다. 사용자가 이를 실제 접수 기능으로 오해할 수 있는 것이 문제다.

재발 방지:

- 실제 메일 발송 전까지는 테스트용/작동 안 함 상태를 화면과 문서에 명확히 남긴다.
- 운영 전 수신 메일을 `contact@yieng.co.kr`로 변경하고 실제 수신 테스트를 한다.
- 폼 기능은 UI 성공 메시지만 보지 말고 메일 수신 또는 서버 저장까지 검증한다.

### 8. 메인 히어로 배경을 바꾸며 `heroCanvas`를 제거할 위험

메인 히어로는 CSS 배경 이미지와 `index.html`의 `heroCanvas` 애니메이션이 함께 구성되어 있다. 배경 이미지를 교체하거나 레이아웃을 수정할 때 `heroCanvas`를 불필요한 요소로 오해해 제거하면 기존 점/불빛 애니메이션이 사라진다.

재발 방지:

- 히어로 배경 이미지는 `assets/styles.css`의 `.hero`에서 관리한다.
- `heroCanvas`는 애니메이션 레이어이므로 배경 이미지 교체 작업에서도 유지한다.
- 히어로 수정 후 데스크톱과 모바일에서 배경, 오버레이, 캔버스가 함께 보이는지 확인한다.

### 9. 요일별 테마가 일부 CSS 변수에만 적용되어 색 일관성이 깨짐

요일별 테마는 `assets/common.js`의 `applyDayTheme()`에서 `--primary`, `--bg`, `--text`, `--primary-soft`를 바꾸는 구조였다. 이후 히어로 오버레이와 주요 버튼, 배너까지 요일 색에 맞추려면 `--hero-tint`, `--hero-tint-strong` 같은 추가 변수가 필요했다. 테마 변수를 일부 요소에만 적용하면 화면 전체가 따로 노는 느낌이 생긴다.

재발 방지:

- 새 컬러 요소를 추가할 때 기존 요일별 테마 변수와 연결할지 먼저 결정한다.
- `--accent`는 기본 레드 계열로 유지하고, 요일별 변화는 `--primary` 계열에 묶는다.
- 요일 테마를 바꾸면 `PROJECT_CONTEXT.md`의 테마 표도 함께 갱신한다.

### 10. 사업분야 페이지 보강 중 원본 정보 일부를 축약함

`business-field.html` 보강 과정에서 긴 텍스트 목록을 이미지 카드 중심으로 재구성하며 일부 항목이 묶이거나 축약되었다. 시각적으로는 좋아졌지만, 원본 사이트의 상세 실적을 모두 보존해야 하는 요구가 있었다면 정보 누락으로 볼 수 있다.

재발 방지:

- 원본 사이트 기반 콘텐츠는 디자인 개선 전에 “보존해야 할 텍스트”와 “요약 가능한 텍스트”를 구분한다.
- 카드화할 때 원본 항목이 빠지지 않았는지 페이지별 체크리스트를 둔다.
- 시각 개선과 정보 보존이 충돌하면 상세 표 또는 접힘 영역으로 원문을 남긴다.

### 11. 이미지 에셋을 많이 추가했지만 용량 최적화가 후순위로 밀림

회사소개와 사업소개 보강 과정에서 `assets/yieng/`에 많은 이미지가 추가되었다. TODO에는 큰 이미지 에셋 최적화가 남아 있다. 정적 사이트에서는 이미지 용량이 첫 화면 로딩 속도와 모바일 사용성에 직접 영향을 준다.

재발 방지:

- 새 이미지 추가 후 파일 크기, 실제 표시 크기, 압축 필요 여부를 확인한다.
- 히어로와 카드 이미지는 표시 크기에 맞는 리사이즈본을 사용한다.
- 이미지 최적화는 디자인 완료 후가 아니라 에셋 추가 작업의 일부로 처리한다.

### 12. HTML 파일에 BOM이나 불필요한 인코딩 변화가 섞임

일부 커밋에서 `<!doctype html>` 앞에 BOM이 들어간 흔적이 있었다. 브라우저에서는 대체로 문제 없이 처리되지만, 정적 파일 비교와 일부 도구에서는 불필요한 변경으로 잡히거나 예기치 않은 표시 문제를 만들 수 있다.

재발 방지:

- HTML/CSS/JS 파일은 가능하면 UTF-8 without BOM으로 유지한다.
- 한글 문서와 코드 수정 후 `git diff`에서 불필요한 첫 줄 변경이 없는지 확인한다.
- 인코딩 변경은 목적이 있을 때만 수행한다.

### 13. 보드 데이터의 저장 위치가 환경별로 달라 사용자가 헷갈릴 수 있음

Node 서버 모드에서는 `data/notices.json`, `data/media.json`가 실제로 갱신된다. 정적 모드에서는 브라우저 `localStorage`가 갱신된다. 두 모드의 화면이 비슷해 보이기 때문에 사용자는 글을 작성했는데 다른 브라우저나 배포 사이트에는 보이지 않는 상황을 버그로 느낄 수 있다.

재발 방지:

- 관리자 기능 설명에는 현재 저장 위치와 반영 범위를 명시한다.
- 운영용 게시글 수정은 가능하면 Node 서버 모드에서 JSON 파일을 갱신한 뒤 커밋한다.
- 정적 모드 테스트 후에는 `localStorage` 때문에 실제 seed JSON과 화면이 달라질 수 있음을 기억한다.

### 14. 배포 후 실제 사이트 확인을 문서 규칙으로만 남기고 자동화하지 않음

`PROJECT_CONTEXT.md`에는 바로가기 생성 후 실제 사이트에 접속해 작동 확인하라는 규칙이 있다. 하지만 자동 테스트나 배포 후 체크 스크립트가 없으면 이 단계가 누락될 수 있다. 특히 GitHub Pages는 캐시와 정적 경로 문제가 뒤늦게 드러난다.

재발 방지:

- 배포 후 `index.html`, 로고, 공용 메뉴, 게시판, 주요 이미지 로딩을 실제 URL에서 확인한다.
- 첫 화면뿐 아니라 하위 페이지의 상대 경로도 점검한다.
- 반복되는 배포 확인 항목은 체크리스트로 남긴다.

## 확정된 실행 규칙

- `OfficialWebsite`와 `OfficialWebsite(Org Backup)` 폴더는 수정, push, pull 대상에서 제외한다.
- 작업 전 프로젝트 루트 문서와 `.cursor/rules/project-rules.mdc`를 확인한다.
- GitHub Pages는 정적 호스팅이며 Node API가 실행되지 않는다는 전제로 설계한다.
- 게시판은 `localhost:3000`에서 서버 모드, 그 외 환경에서 정적 모드로 동작한다.
- 정적 모드 게시판 수정은 브라우저 `localStorage`에만 저장된다.
- 실제 운영 게시판이 필요하면 서버 API, CMS, 폼/DB 서비스를 별도로 붙인다.
- 로고, 이미지, CSS, JS 변경 후에는 GitHub Pages 실제 URL에서 로딩을 확인한다.
- 공용 스크립트 변경 후 캐시 문제가 의심되면 버전 쿼리를 갱신한다.
- `ShortCut/*.url`에는 ASCII URL만 저장하고, 생성 후 직접 접속 확인한다.
- `contact.html` 문의 폼은 실제 메일 발송 전까지 테스트용으로 취급한다.
- `heroCanvas`는 메인 히어로 애니메이션 레이어이므로 삭제하지 않는다.
- 요일별 테마 변경 시 `assets/common.js`, `assets/styles.css`, `PROJECT_CONTEXT.md`를 함께 확인한다.
- 이미지 추가 후 용량과 표시 크기를 점검한다.
- HTML/CSS/JS는 불필요한 BOM이나 인코딩 변경을 만들지 않는다.
